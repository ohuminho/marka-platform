# MARKA Phone OTP Authentication — Implementation Plan

## Approved product decision
- One MARKA identity shared by Marketplace and Mobility.
- Phone is a first-class sign-in and verification identifier; Angola defaults to +244 and international numbers use E.164.
- Email becomes optional, not removed. Existing email accounts remain valid.
- Password remains normal sign-in. OTP is for initial phone verification, phone changes, phone-based recovery and sensitive re-authentication. No OTP on every login.
- Phone OTP delivery is SMS only. WhatsApp is out of scope.
- Existing email verification and recovery remain on the current Resend integration.
- MIMO Verify is the selected SMS delivery provider for Angola. Integration is prepared; production sending stays disabled until Backbone supplies credentials and confirms the API authentication/response contract.

## MIMO Verify public API findings
The official MIMO Verify page documents:
- Endpoint: POST https://verify.mimo.ao/v1/otp/send
- Request fields: recipient (E.164), channel ("sms"), code (generated by MARKA), expires_in (seconds).
- MARKA generates and validates OTP; MIMO Verify transports it.
- Published Angola SMS tariff: 10.90 AOA/message, VAT applies; published coverage includes Unitel, Movicel and Africell.
- WhatsApp and email channels exist in MIMO Verify but are not used by MARKA.

The public page does not document the authentication header, full response schema, delivery receipt/status endpoint, balance endpoint or minimum top-up. The adapter must fail closed until Backbone confirms these details. Do not guess Bearer, Basic or custom-header authentication.

Existing MARKA email provider is Resend (RESEND_API_KEY, RESEND_FROM_EMAIL). Keep it independent of MIMO Verify.

## MIMO activation checklist — request from Backbone
1. Production API key and exact authentication header name/value format.
2. Sandbox/test credentials and test destination rules.
3. Complete success/error response examples, including provider message/request ID.
4. Delivery receipt/status API or webhook specification.
5. Balance/credit query API and low-balance behavior.
6. Confirmed Angola tariff, VAT treatment, minimum top-up, credit expiry and payment channels.
7. Sender ID requirements and whether Verify uses a managed sender.
8. Rate limits, timeout/retry guidance, data-processing terms and support escalation.

Do not send real SMS until details are confirmed, credentials are stored in Vercel Environment Variables, a controlled test is approved and the monthly budget cap is configured.

## Environment variables
- MIMO_VERIFY_API_KEY: secret API key.
- MIMO_VERIFY_AUTH_HEADER_NAME: exact header name confirmed by Backbone.
- MIMO_VERIFY_AUTH_HEADER_VALUE: exact header value/template confirmed by Backbone; may contain literal placeholder {API_KEY}.
- MIMO_VERIFY_BASE_URL: optional; defaults to https://verify.mimo.ao.
- PHONE_OTP_PEPPER: secret HMAC pepper, at least 32 characters.
- PHONE_OTP_MONTHLY_BUDGET_AOA: monthly spend cap; initial planning envelope 15000.
- PHONE_OTP_MAX_SENDS_PER_PHONE_PER_HOUR and PHONE_OTP_MAX_SENDS_PER_IP_PER_HOUR: abuse limits.
Never commit secrets or expose them client-side.

## OTP security policy
- Cryptographically random 6-digit code; store only keyed HMAC, never plaintext.
- Five-minute expiry; single use; atomic consume.
- 60-second resend cooldown.
- Maximum 5 sends per phone per rolling hour and 10 per IP per rolling hour (configurable defaults).
- Maximum 5 incorrect attempts per challenge; then invalidate.
- Generic responses to avoid account enumeration.
- Normalize phone to E.164 before lookup and uniqueness checks.
- Never log OTP, provider credentials, full phone numbers or raw request bodies.
- Treat provider timeout as ambiguous; reconcile before retry to avoid duplicate paid messages.

## Cost control and operations
- Published Angola tariff reference: 10.90 AOA/SMS plus VAT; reconfirm commercial terms before activation.
- Record requested, accepted, delivered, failed and rejected SMS with provider, destination hash, message ID, tariff snapshot, currency and timestamps.
- Distinguish API acceptance from confirmed delivery.
- Super Admin dashboard: sends, delivery rate, retries, spend, estimated spend, provider balance (only if supported), per-country cost, daily/monthly caps.
- Alerts at 50%, 75%, 90% and 100% of configured monthly budget.
- On depleted balance or budget cap, stop new paid sends; existing valid challenges can still be verified.
- Initial planning envelope: AOA 15,000, not a payment instruction. Reconcile VAT and exact tariff before production.
- No WhatsApp spend, credentials, templates or delivery logic.

## Database implementation status
- A Prisma schema foundation and migration `20261105090000_add_phone_otp_sms_ledger` have been added on the feature branch.
- `User.phoneE164` is nullable and unique; existing `Profile.phone` remains display/contact data only.
- `PhoneOtpChallenge` stores the challenge hash, purpose, expiry, attempts, consume state and delivery state.
- `SmsDeliveryLedger` records provider, hashed destination, delivery lifecycle, optional tariff snapshot and timestamps.
- A protected Super Admin usage API and dashboard page expose monthly budget, recorded spend, delivery states, country breakdown and provider readiness. They do not send SMS or query a MIMO balance.
- Mobility contact verification now accepts either a verified phone or a verified email. Government identity/KYC and driver-document checks remain separate and mandatory.
- Existing `User.email` and `User.emailNormalized` remain required in this phase. Making them nullable is intentionally deferred until registration, login, verification, recovery, profile, admin, Marketplace, Mobility and notification paths are audited and refactored together. This avoids creating phone-only accounts that current application flows cannot safely support.
- Existing email users, Resend verification/recovery and sessions are unchanged.
- The migration is not applied to production. It still requires Prisma validation and isolated-database migration testing before release.

## Application integration sequence
1. Audit required-email assumptions across registration, login, recovery, profile, admin, Marketplace, Mobility, notifications and exports.
2. Add country picker and phone-first registration with optional email.
3. Add OTP request/verify APIs with abuse controls and MIMO Verify SMS adapter.
4. Update login to accept email or E.164 phone plus password.
5. Add phone-based recovery and change-phone confirmation.
6. Add Super Admin SMS cost dashboard and budget circuit breaker.
7. Test on isolated DB; run unit/integration tests; stage behind feature flag.
8. Enable paid SMS only after Backbone confirms API contract, credentials and controlled test budget approval.

## Release gates
- Existing email sign-in and recovery continue through Resend.
- Phone-only account can register, verify and sign in.
- One phone cannot belong to two users.
- OTP is single-use and expires correctly.
- Resend and brute-force limits enforced server-side.
- No paid SMS in tests unless explicit test provider is configured.
- SMS outage/depleted balance does not break email login or existing sessions.
- No WhatsApp delivery path.
- No production schema migration before reconciliation.
